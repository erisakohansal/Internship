# AGENTS.md — MOPD

## 1. Purpose

MOPD ("MCQA-Only Partial Domain"?) is a smoke-test/isolation variant of the multi-domain RL stage (see `../multi-domain-RL/AGENTS.md`): same GRPO recipe, but trained only on the MCQA sub-task, used to isolate whether an issue observed in the combined multi-domain run is domain-specific. It is **not** a Cascade 2 paper stage in its own right — it's a debugging tool built on top of Stage 2.

**Naming ambiguity — the real stage is confirmed NOT implemented here yet.** This folder name coincides with a real Cascade 2 stage (§4.4 "Multi-domain On-Policy Distillation," Stage 3 of the pipeline: IF-RL → Multi-domain RL → **MOPD** → RLHF). What's actually inside this folder right now (`launch.sh` training only on `mcqa-{train,test}.parquet`, `experiment_name=mopd`) is confirmed to be the MCQA-isolation smoke test described below, not the paper's on-policy distillation stage — treat the two as unrelated things sharing a folder name until the real stage is built.

**Reference implementation for the real §4.4 stage, if/when it's built**: found in NeMo-**RL** (not Gym, since this is a training-loop algorithm, not a task environment) — see `../NEMO_RL_GYM_REFERENCE.md` §6 for full detail. Three files implement it: [`nemo_rl/algorithms/opd.py`](https://github.com/NVIDIA-NeMo/RL/blob/main/nemo_rl/algorithms/opd.py) (per-domain teacher routing), [`advantage_estimator.py::OPDAdvantageEstimator`](https://github.com/NVIDIA-NeMo/RL/blob/main/nemo_rl/algorithms/advantage_estimator.py) (reverse-KL token-level distillation advantage: `sg[log π_teacher − log π_student]`, matching the paper's Eq. 2), and [`loss_functions.py::ClippedPGLossFn`](https://github.com/NVIDIA-NeMo/RL/blob/main/nemo_rl/algorithms/loss/loss_functions.py) `icepop` truncated-IS mode (hard zero-out gate outside `[ε_low, ε_high]` = `[0.5, 2.0]` per the paper, matching Eq. 3 exactly). Useful shortcut for a VERL port: VERL's own `rollout_is_threshold="lower_upper"` mode (see `VERL_MECHANICS.md` §3.9) already implements the same ICE-POP-style masking — porting this stage would mainly need (a) teacher-checkpoint routing and (b) a teacher forward pass for `log π_teacher`, not new IS-masking logic. No public end-to-end example config exists even in NeMo-RL for the multi-teacher variant specifically — you'd be assembling it from these building blocks either way.

## 2. Current mechanism

`launch.sh` is a near-duplicate of `../multi-domain-RL/launch.sh` with three differences: `trainer.experiment_name=mopd`, `trainer.total_training_steps=10` (vs. 70), and pointing `data.train_files`/`data.val_files` at `mcqa-{train,test}.parquet` instead of `multi-domain-RL-{train,test}.parquet`. All other hyperparameters (batch 128, `rollout.n=16`, `ppo_epochs=1`, length budgets, `rollout_correction` settings, `filter_groups`, `fsdp_config.model_dtype=fp32`) are identical to the combined run.

**Important quirk, confirmed from source**: this script sets `PWD="…/multi-domain-RL"` and `cd $PWD` (line 26-27) before running — so it actually executes out of the `multi-domain-RL/` directory and uses **`multi-domain-RL/reward.py`** (via `multi_domain_reward_fn`, dispatching to `mcqa_reward_fn` since only MCQA data is loaded), not this folder's own `reward.py`. This folder's own `reward.py` and `prepare_data.py` are both **empty files (0 bytes)** — unused placeholders, not a second implementation.

It also expects `multi-domain-RL/data/mcqa-train.parquet` / `mcqa-test.parquet`, which **do not currently exist in the repo** (only `multi-domain-RL-train.parquet`/`-test.parquet` are present, i.e. the pre-blended 3-domain dataset). This file must be generated separately (e.g. filtering `prepare_data.py`'s output to the MCQA rows, or a dedicated single-domain prep step) before this script can run — it's not something that gets created automatically.

Gradient clipping: no override in this script, so VERL's default (`grad_clip=1.0`, confirmed in `verl/workers/config/actor/dp_actor.yaml:29`) applies. `compute_grad_norm()` (`verl/utils/torch_functional.py:365`) logs the **pre-clip raw norm** — the actual applied update is still clipped to 1.0 downstream, regardless of what's logged.

## 3. Open issues / TODOs

1. **~~`grad_norm≈4` on the MCQA-only run is unexplained~~ — resolved, see `../multi-domain-RL/AGENTS.md` §3.1.** Confirmed from real wandb logs (run `dxqyxpo4`): `grad_norm` climbs monotonically 0.66→4.11 over 8 steps in lockstep with `response_length/mean` collapsing 69→8.9 tokens — the model rapidly learns terse boilerplate answers, and `loss_agg_mode=token-mean` divides the same total loss by a shrinking token-count denominator, mechanically inflating the per-token/total gradient norm. Confirmed **not** present when MCQA trains inside the blended multi-domain run (`z46psk6k`: grad_norm stays bounded 0.13-1.4 the whole 69 steps) — this is an artifact of the short (10-step), narrow, single-domain isolation setup rapidly overfitting a small prompt distribution, not a bug in the recipe or a property of MCQA itself.
2. **Missing `mcqa-train.parquet`/`mcqa-test.parquet`**: generate these (single-domain slice of the multi-domain dataset, or a dedicated prep script) before relying on this launch script again — currently it will fail at the `TRAIN_FILE`/`TEST_FILE` load step if those parquet files aren't present on the cluster.

This folder's `reward.py`/`prepare_data.py` are empty — either populate them with a real MCQA-only implementation (if true domain isolation at the reward level is ever needed) or remove them to avoid confusion, since right now `launch.sh` silently ignores them in favor of `multi-domain-RL/reward.py`.
